# Prompt reutilizable para portaciones a React y EureUI

Versión inicial en construcción. Este prompt evoluciona con la portación de Familias y las devoluciones del usuario. Las reglas acordadas se distinguen de las propuestas y de los resultados todavía pendientes de validar.

## Prompt para usar en otro proyecto

Trabajá en la modernización del proyecto indicado, utilizando como referencia una aplicación existente con React y componentes EureUI. Desarrollá por etapas comprobables y mantené actualizados tanto el plan como este prompt con lo aprendido.

Contexto que debés resolver antes de implementar:

Respetar el alcance confirmado por cliente y canal. En Familias, la entrega del 2 de noviembre de 2026 es solo para IFES y la app móvil debe permanecer igual. No interpretar la modernización web como autorización para portar sus vistas embebidas ni modificar la API. Auditar rutas, recursos y helpers compartidos antes de limpiar legacy; conservar consumidores móviles y registrar límites de la verificación.

- Proyecto de destino y carpeta de referencia.
- Si el destino es experimental y cuál es el sistema que podría reemplazar.
- Framework, PHP, dependencias y entorno de ejecución instalados, además de las versiones declaradas.
- Base de datos, procedimientos, autenticación, integraciones externas y consumidores de la API.
- Versiones reales del motor de base de datos y nivel de compatibilidad en desarrollo y producción; distinguir versiones confirmadas de estimadas. En Familias se confirmó SQL Server 2019 local (`15.0.2200.2`) con compatibilidad 100 e idioma Español; producción probablemente usa 2014, aún por confirmar. No introducir funciones incompatibles con el nivel de la base aunque el motor sea reciente (por ejemplo, `TRY_CONVERT` fue rechazado en desarrollo). Una prueba con procedimientos simulados no verifica conversiones de fechas del driver ni compatibilidad del servidor real.
- Institución o cliente inicial y configuración que identifica al cliente.

Consultá primero el código, las instrucciones del repositorio y el contexto disponible. Preguntá únicamente por información importante que no puedas obtener de esas fuentes. Respetá las restricciones de herramientas, instalación de dependencias, Git y servicios externos del entorno de trabajo.

### Analizar antes de trasladar

Seguí los recorridos desde rutas y controladores hasta vistas, scripts, modelos y servicios. Identificá qué lógica está dentro de las vistas y deberá prepararse en el backend para React. Distinguí pantallas activas, variantes por cliente, vistas consumidas por otras aplicaciones y archivos de prueba u obsoletos.

Inspeccioná los componentes de la aplicación de referencia y sus dependencias reales. Separá lo reutilizable de sus logos, colores, rutas, roles y reglas de negocio. No presupongas que un nombre de componente implica una funcionalidad completa; un indicador de progreso no es un sistema de carga de archivos.

### Actualizar la base técnica

En llamadas a procedimientos SQL Server con fechas, no depender de la conversión implícita del texto generado por el driver. Revisar los tipos reales de los parámetros y usar formato y conversión explícitos compatibles con el motor y nivel de compatibilidad de destino. En Cuenta corriente se conserva `Y-m-d H:i:s.v` y se convierte con `CONVERT(smalldatetime, ?, 121)` en una variable local antes de `EXEC`, manteniendo valores parametrizados. No quitar fracciones ni cambiar la ventana de consulta para ocultar un error de formato: `smalldatetime` redondea y puede cambiar el día. Separar correcciones de transporte de decisiones sobre límites inclusivos y fin de mes. Validar con el servidor real además de pruebas simuladas; no prometer compatibilidad universal a partir de una única versión.

Al portar el cambio de contraseña, conservar conscientemente la política vigente y comprobar la contraseña actual y la confirmación en servidor. Usar componentes de contraseña con mostrar/ocultar y atributos de autocompletado correctos. No guardar secretos en borradores, `old input` ni props: revisar `withInput`, `dontFlash` y los nombres personalizados de campos. Excluirlos de `TrimStrings` para no recortar contraseñas silenciosamente. Autorizar contra la cuenta autenticada y mantener CSRF y prevención de doble envío. Comprobar que la sesión actual continúa y las sesiones web antiguas se invalidan; tras una actualización de Laravel, probar además la redirección HTML al login y el 401 JSON del middleware `auth.session`. Mostrar confirmación en una pantalla que realmente consuma el aviso. No extender el cambio a tokens o APIs móviles por accidente. Probar con cuentas aisladas, sin cambiar contraseñas reales.

Si se decide actualizar el framework, hacelo como etapa separada antes de reemplazar pantallas. Revisá las guías oficiales de todas las versiones mayores atravesadas. Conservá la estructura existente cuando sea compatible y evitá cambios de configuración ajenos al objetivo.

Definí pruebas de los comportamientos existentes antes de modificar dependencias. Aislalas de credenciales, bases y servicios reales. Compará resultados antes y después del cambio. No afirmes que la actualización terminó si solo se modificó el manifiesto: confirmá las versiones instaladas y los resultados del nuevo entorno.

Después de actualizar paquetes de vistas, verificá también las plantillas compiladas. Ante un método inexistente, compará el archivo compilado con la plantilla fuente instalada antes de modificar código. Limpiá la caché local afectada y repetí las pruebas; evitá una limpieza global que pueda alcanzar caches compartidos.

Al copiar un proyecto experimental, verificá que los enlaces de almacenamiento sigan siendo enlaces y apunten al destino correcto. Si un archivo existe pero su URL falla, comprobá el disco configurado, el enlace público y la respuesta HTTP exacta. Preservá cualquier contenido existente antes de reparar enlaces y distinguí un enlace roto de archivos históricos ausentes en la copia.

Confirmá si existe un concentrador de archivos compartido entre aplicaciones antes de elegir el destino del enlace. Tanto la raíz del disco usado para subir archivos como la URL pública deben llegar al mismo almacenamiento. En Windows pueden usarse junctions para directorios. Conservá aparte los archivos generados localmente y reconciliá su incorporación al concentrador sin sobrescribir archivos ni escribir fuera de los permisos disponibles. Un proyecto experimental puede compartir archivos reales con otros sistemas.

Cuando una restricción impida instalar dependencias, prepará los cambios permitidos, explicá el paso exacto que debe ejecutar el usuario y registrá la validación pendiente. No modifiques locks a mano ni copies dependencias de otros proyectos para eludir esa restricción.

### Modernizar la interfaz

Cuando el usuario descarte una variante experimental, retirar su ruta, página, estilos exclusivos, enlaces/props de comparación y pruebas específicas. Conservar el inicio elegido y las demos independientes; actualizar la documentación para que las propuestas históricas no se confundan con opciones vigentes. En Familias, Home2 se descartó el 2 de noviembre.

Antes de reemplazar pantallas funcionales, preparar una ruta demo UI. Para una galería con datos ficticios y sin efectos sobre el negocio, permitir acceso público cuando el usuario lo solicite para agilizar la revisión; conservar la autenticación de las pantallas reales. Mostrar componentes reales reutilizables y permitir ver cómo cambia toda la interfaz al editar el tema. Los ajustes del usuario se aplican a los mismos componentes que luego usarán las pantallas reales.

Si se agrega un panel de colores, distinguir claramente vista previa y persistencia: probar cambios en memoria, restablecer el archivo recibido y exportar un tema completo. No introducir una escritura administrativa al servidor para una demo. Mostrar las combinaciones de texto/fondo relevantes y conservar el archivo del cliente como fuente de verdad.

Usá React, TypeScript y EureUI con la integración de backend acordada. Para un proyecto Laravel, evaluá Inertia para conservar rutas y autenticación del servidor. No importes automáticamente el modelo de usuarios de la referencia.

Usar EureUI significa portar o reutilizar los componentes reales de la referencia, no escribir controles parecidos y ponerles nombres «Eure». Leer su implementación, contrato de props, composición, estilos y dependencias antes de usarlos. Registrar origen y adaptaciones necesarias, y distinguir la portación de un subconjunto de la adopción del catálogo completo. En Familias, el usuario detectó esta desviación en el login; se corrigió con `EureInputGroup`, `EureInput` y `EureButtonPrimary` portados, conservando el tema institucional. Si se traducen clases de Tailwind a CSS local o se excluye una capacidad que requiere una dependencia ausente, hacerlo explícito y no anunciar esa capacidad como disponible.

Organizá la información en tarjetas, mantené breadcrumb y franja superior de color, y diseñá una navegación coherente en escritorio y celular. Conservá las fotos como recurso de reconocimiento mediante un avatar reutilizable. Modernizá los recorridos sin cambiar silenciosamente su significado funcional.

Revisá la arquitectura del menú, no solo su apariencia. Si repite un árbol extenso por cada entidad, considerar un selector con nombre y foto y un único conjunto de accesos directos; separar navegación general, acciones de la entidad y perfil. Mantener visible el contexto seleccionado y los pendientes de las demás entidades. En Familias se aplicó por pedido explícito del usuario: selector de alumno, enlaces directos sin el tercer nivel de AdminLTE e inicio con las tarjetas de todos los hijos. Recordar una selección en el navegador nunca sustituye las comprobaciones de pertenencia del backend.

Antes de reutilizar getters de modelos para preparar props, comprobar si escriben datos. En Familias, los accesos antiguos a fotos podían crear usuarios o registros de alumno; el nuevo inicio lee las imágenes existentes y usa iniciales si faltan. Verificar que las consultas de inicio y contadores no adelanten lecturas ni produzcan altas silenciosas. Para totales familiares, distinguir comunicaciones únicas de su presencia en varios alumnos; para contenido HTML histórico, aislar la vista previa del documento principal y mantener el acceso al contenido completo.

Centralizá todos los colores de interfaz en archivos de tema. Cada cliente debe tener un archivo completo e independiente con la misma estructura de variables, seleccionado a partir del identificador configurado. No usar herencia ni sobrescrituras parciales entre temas de clientes. Empezá con uno y agregá los demás en la etapa correspondiente. Las fotos, logos y colores del contenido HTML histórico tienen tratamiento separado.

### Resolver temprano los componentes difíciles

Comprobar el formato persistido de las URLs del editor anterior: conservar el disco no garantiza conservar el HTML. En Familias el Blade insertaba `/storage/archivo`; la portación introdujo involuntariamente dominio y puerto mediante `Storage::url`. El usuario confirmó guardar rutas relativas al dominio para imágenes y emojis. Verificar carga, recuperación de borradores, guardado y lectura desde otros consumidores. Convertir únicamente URLs autorizadas de archivos del borrador; quitar indiscriminadamente el dominio de cualquier URL puede aceptar recursos ajenos. Distinguir corregir nuevos envíos de modificar mensajes históricos.

Probar al comienzo el editor enriquecido con emojis, pegado/carga de imágenes y adjuntos, y la selección de fotos con recorte. Incluir progreso, errores, archivos pendientes, cancelación y uso desde celular. Verificar la presentación del contenido histórico.

No asumir que emojis Unicode equivalen visualmente a los del editor anterior. En Familias el usuario prefirió recuperar sus dibujos: se extrajo el catálogo gráfico local a PNG individuales con rutas versionadas y estables, y se creó un selector React con categorías, búsqueda en español y recientes. Conservar procedencia y recursos de mensajes históricos; permitir solo imágenes conocidas del catálogo en los limpiadores de cliente y servidor. Estos emojis se guardan dentro del HTML a tamaño uniforme, sin tratarlos como adjuntos ni ofrecerles los controles de tamaño de fotografías. La preferencia gráfica corresponde a este proyecto; revisar el catálogo real y acordar el resultado en cada portación.

Revisar los efectos de las solicitudes: abrir una pantalla puede marcar una comunicación como leída, y precargarla no debe adelantar esa acción. Preservar permisos, contexto del alumno o entidad, validaciones y confirmaciones definitivas.

### Entregar y retirar por etapas

Al elegir el usuario una variante visual, registrar la decisión y conservar las demos como referencia. Convertir el layout elegido en un contenedor real alimentado por el backend; mantener ejemplos y herramientas de diseño dentro de las demos. Para la primera entrega funcional, recorrer login, redirecciones intermedias e inicio: una cartelera obligatoria u otra pantalla previa puede formar parte del ingreso aunque no se llame «home». Conectar solo acciones respaldadas por reglas reales; los botones ficticios de una demo de notificaciones no definen nuevas reglas de lectura. Durante la convivencia con Blade, usar navegación completa hacia pantallas que aún no responden con Inertia.

Cada etapa de interfaz debe ofrecer algo visible y utilizable, con navegación, datos y manejo de errores. La etapa técnica puede conservar el aspecto previo. Diferenciá las demostraciones con datos ficticios de los recorridos que guardan o envían información.

Conservá cada vista antigua hasta validar su reemplazo y sus consumidores. Después retirala junto con los assets exclusivos; mantené los parciales compartidos hasta sustituir su último uso. No acumules carpetas permanentes de código obsoleto. Retirá AdminLTE y plugins al terminar sus usos. Con Inertia puede permanecer una plantilla Blade mínima de arranque.

### Aprender de las devoluciones

Cuando el usuario quiera mostrar alternativas a otra persona, conservar la demo ya revisada y crear una ruta distinta para cada propuesta. Identificar las opciones y facilitar pasar de una a otra. Compartir datos de muestra, componentes y contrato de temas; aislar los estilos de cada diseño para no transformar la opción anterior. Distinguir la creación de una alternativa de su aprobación: en Familias, el usuario pidió opciones para Mariela, pero no eligió todavía una ganadora.

Para comparar variantes de layout, mantener el mismo contenido principal cuando el usuario lo solicite: bienvenida, textos, imágenes, tarjetas, orden y acciones. Reutilizar la misma composición, sin ocultar bloques por variante ni introducir títulos distintos. En Familias pidió explícitamente igualar el contenido de la alternativa después de unificar el tema; las diferencias quedan en la estructura del menú y el encabezado.

Si pide variaciones del diseño inicial, conservar su estructura reconocible. Revisar el layout que realmente usan las pantallas del proyecto de referencia: seguir el selector de rol hasta su contenedor, menú, encabezado, breadcrumb y pie de usuario, y mirar una pantalla funcional con tarjetas. No deducir el layout a partir de componentes aislados ni del starter que puede no usarse. En Familias, el usuario corrigió la propuesta horizontal y pidió una variante lateral más cercana a Pranzo. Mantener los colores de cada propuesta en un archivo completo separado cuando compararlas requiera paletas diferentes, sin alterar la opción ya revisada; el editor debe indicar el archivo de destino correcto.

Permitir que el bloque inferior del menú (perfil y acciones de sesión o regreso) tenga identidad independiente del resto de la navegación. Usar tokens del tema para fondo, texto, texto secundario y separadores, y exponerlos en la galería. El usuario pidió expresamente esta separación al revisar Familias; no resolverla con colores fijos ni con un archivo aparte del tema del cliente.

Separar la referencia de layout de su identidad cromática. Que al usuario le guste la estructura de otro proyecto no implica que quiera sus colores de marca. En Familias pidió quitar el verde y amarillo de Pranzo y luego aplicar a la segunda demo el mismo tema que al original. Cuando solicite compartir tema, hacer que los layouts lean el mismo archivo completo del cliente, sin copiar valores a archivos que puedan divergir. Conservar la estructura de cada opción y mostrar el destino correcto en el editor. Comprobar el contraste de las combinaciones usadas para texto y conservar colores semánticos diferenciados para éxito, advertencia y error.

Incluir la campana de notificaciones en la revisión de la estructura visual: contador, panel, estados pendientes/leídos y avatares cuando corresponda. No dar por cubierta esa función por tener un icono de campana dentro de una tarjeta de componentes. En la demo usar ejemplos locales; al conectar el sistema real, revisar el contrato existente y preservar las reglas de lectura. Esta enseñanza surge del primer feedback visual de Familias.

Después de cada revisión, registrá la devolución concreta del usuario, la decisión resultante y el cambio realizado. Actualizá este prompt cuando la enseñanza sea aplicable a otras portaciones. Mantené los nombres y detalles del negocio en el plan específico.

No conviertas propuestas del agente en preferencias del usuario. Diferenciá decisiones acordadas, código preparado y comportamiento verificado. Informá qué cambió, cómo se comprobó y qué falta.

## Aprendizajes iniciales y validaciones pendientes

- Cuenta corriente y pagos: separar la portación visual de las reglas financieras. Reutilizar el procedimiento y el helper de totales; trasladar explícitamente la clasificación que estuviera en el Blade y probar precedencia, saldo cero, créditos, fecha nominal y fin/inicio de mes. No «arreglar» condiciones o ventanas de fechas heredadas sin acordarlo. Mantener importes sugeridos independientes de la búsqueda local. Verificar el formato exacto que espera el POST de pago: un valor visual con símbolo o puntos de miles puede cambiar de significado o ser rechazado por el parser. Usar texto decimal canónico y no deducir separadores ambiguos. Conservar medios configurados, CSRF, redirecciones y controlador de pago; probar su despacho con proveedores simulados, sin crear intenciones reales. En recibos, preservar responsable de cobro, estado pendiente/confirmado y enlaces existentes, incluso si el enlace del número y el botón PDF tienen condiciones distintas. Fechas relativas fuera de enlaces mediante `EureHumanDate`. Distinguir pruebas locales de las comprobaciones pendientes con SQL Server, PDF y pasarelas reales.

- Inasistencias: comprobar cómo se calculan los totales antes de presentar indicadores. En Familias se suma el campo `imputar`, no la cantidad de filas; un registro puede pesar cero o una fracción, y su descripción no autoriza recalcularlo. «Mes» y «semana» eran períodos móviles calculados con `subMonth()` y `subDays(7)`, no mes calendario ni semana iniciada el lunes. Conservar límites y fuente, explicitar etiquetas y probar los bordes temporales. Mantener las cuatro columnas y controles locales de DataTables; no ocultar observaciones en celular ni hacer que buscar modifique los totales institucionales. No inventar justificaciones editables o filtros que no existían. Conservar fechas de calendario exactas cuando ese sea el dato; si se pide formato relativo, usar `EureHumanDate`. Distinguir mejoras de presentación (en esta entrega orden inicial por fecha y quitar símbolo monetario de cantidades) de cambios de reglas de asistencia.

- Documentación: distinguir documentos emitidos por la institución (informes/certificados con reglas de habilitación) de archivos aportados al legajo. Conservar el proveedor, sus bloqueos, mensajes y comprobación de disponibilidad al descargar; no convertir un informe bloqueado en un enlace directo ni exponer rutas internas de reportes. Las fechas deben provenir de datos existentes. Al portar cargas de legajo, validar relación responsable/alumno en GET y POST, formatos y tamaño en servidor y no aceptar un token arbitrario para vincular archivos. En esta entrega se eligen archivos localmente y se suben al confirmar: no quedan pendientes al cancelar antes del guardado. Verificar que llegue el lote completo, revertirlo ante fallos y hacer idempotente el reintento tras perder una respuesta. Mantener el contrato compartido de entidad/nombre de archivo; no agregar eliminación de documentos guardados si no existía. Revisar rutas web antiguas que eludan las nuevas comprobaciones, preservando las APIs móviles. Pruebas con disco/base aislados no validan el proveedor PDF real ni la presentación visual.

- Decisión definitiva sobre recibidas: conservar el comportamiento de Blade/DataTables. El servidor carga TODAS las comunicaciones que cumplen remitente/fechas/solo sin leer. Búsqueda global, orden por columnas, tamaño de página y paginación son locales sobre ese conjunto completo. El usuario rechazó la paginación de servidor y la búsqueda restringida a una sola página. No introducir esos cambios sin acordarlos. Se revisó EureDataTable de Pranzo: usa TanStack y XLSX, ausentes aquí; ReceivedTable conserva el comportamiento con React existente y no se presenta como una portación literal de EureDataTable.
- Probar los filtros con la serialización real del cliente: Inertia envía booleanos GET como `true`/`false`, mientras que la regla `boolean` de Laravel no acepta esas cadenas. Normalizar esas dos cadenas antes de validar, conservando el rechazo de valores inválidos. Una prueba solo con `1`/`0` no detectó el fallo que impedía aplicar filtros y mostrar «Filtrados»; se agregó una regresión con URLs generadas por Inertia.
- Preservar «Filtrados», resumen de filtros aplicados y «Limpiar». La fecha inicial debe venir explícitamente como parámetro `desde` desde barra lateral, home, ficha, campana y accesos Blade; centralizar esos enlaces en `FamilyPortal::receivedUrl`. El listado sin parámetros NO agrega filtros. «Limpiar» navega a la URL sin query, vacía todos los filtros y reinicia búsqueda/orden/paginación locales. El indicador refleja restricciones reales, no una bandera enviada por el cliente.
- Feedback de densidad en recibidas: reducir espacio desperdiciado no autoriza ocultar controles existentes. El usuario rechazó los filtros plegados: deben permanecer visibles en una tarjeta «Filtros», con remitente, desde, hasta, solo sin leer, Filtrar y Limpiar, siguiendo la disposición de Blade. Separar la búsqueda general y los controles de la tabla, como en DataTables. Buscar sobre el resultado de los filtros aplicados sin aplicar cambios pendientes del formulario. Conservar fotos, estados y fechas interactivas separadas del enlace a detalle. El diseño de tabla compacto todavía requiere aprobación visual del usuario.
- Fichas rápidas: reutilizar `FamilySenderQuickCard` para emisores. Recibe `sender` (nombre, avatar, descripción, perfil y materias opcionales), `studentName` opcional, contenido del disparador y clase opcional; no anidar enlaces ni botones dentro del disparador. Primera integración: foto/nombre del emisor en recibidas. Feedback: usar el nombre como título en lugar de «Ficha del emisor», foto grande (176 px) e información útil disponible. Las materias corresponden al docente y grupo del alumno consultado, sin duplicados ni cursos ajenos; cargarlas en lote. Abrir la ficha no navega a la comunicación ni registra lecturas; los datos llegan con el listado autorizado. Mostrar solo campos explícitos de presentación, sin agregar datos de contacto automáticamente. Reutilizar el diálogo existente, colores del tema y alternativa con iniciales; mantener cierre por teclado y retorno del foco.
- Perfil propio del responsable: preservar datos, relaciones, curso/plan y accesos existentes. En el legacy «Editar perfil» solo cambia la foto; no convertir datos personales de consulta en campos editables sin acordarlo. Autorizar tanto lectura como guardado contra la sesión, distinguiendo ID del responsable (GET) e ID del usuario (POST). No serializar el modelo completo ni llamar getters que creen usuarios o fotos. Reutilizar `FamilyPhotoEditor` y `FamilyPhotoUpload` para fotos de alumnos y responsables, con recorte y guardado explícito, normalización y conservación de archivos compartidos. Mantener el enlace a contraseña mientras su pantalla continúe en Blade; no alterar la API móvil con la migración web.
- Enviadas y respuestas: separar «la institución leyó mi mensaje» de «yo leí su respuesta». Solo abrir el detalle marca la respuesta propia; listar, buscar, ordenar, cambiar página, consultar fechas o abrir una ficha rápida no registra lecturas. Mantener todo el historial y DataTable local cuando así funcionaba el legacy; no trasladar automáticamente el período inicial de recibidas.
